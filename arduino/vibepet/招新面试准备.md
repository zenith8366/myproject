## 零、进场前 5 分钟

### 0.1 一句话版本（背下来，一字不改）

> 我做了个放在桌上的小设备。平时我们用 AI 写代码，它干完活、或者卡在等你确认一条命令上，
> 你不看终端就不知道。这个小设备能实时显示 AI 在干什么，需要你批准的时候会响三声、
> 屏幕上弹出要执行的命令，你按一下设备上的按钮就能批准或拒绝——不用切回终端。

### 0.2 五个必须记住的数字

| 数字 | 含义 | 怎么说 |
|---|---|---|
| **7** | 七种状态 | 空闲、工作中、待审批、完成、出错、失联、请到电脑答题 |
| **104** | 自动化测试总数 | 电脑端 49 例（12/14/14/9）+ 固件端离线 55 例 |
| **394** | 中文字库字数 | 95 个 ASCII + 299 个汉字，约 9.1 KB |
| **30882 / 1299** | Flash / RAM 占用 | 32256 里用 30882（约 96%）；2048 里用 1299（约 63%） |
| **6 周** | 开发周期 | 约 6 周、56 次提交、34 个跟踪文件 |

### 0.3 三个必须能讲清的取舍

1. **为什么分成两个程序**：串口是独占的，而且一打开板子就复位；Hook 每次都会新起一个
   短命进程，承受不了“现开现关”。所以让一个常驻 daemon 抱着串口，短命进程只走本地 Socket。
2. **为什么拿不准就拒绝**：审批链路出错的后果不是“显示错了”，而是“该拒绝的没拒绝”。
   超时、连不上、解析失败，终点全是 deny。
3. **为什么整行限制 320 字节**：审批请求最坏 258 字节，收到 256 会静默丢整条；
   320 留出余量，同时用 `clamp_bytes()` 按 UTF-8 边界截断，不切碎汉字。

### 0.4 三个真实踩过的坑（选一个展开就够）

1. **屏幕点不亮**：ESP32 方案背光亮、无画面，换库、换引脚、换 SPI 速度都没解决；
   最后换到有已验证例程的 UNO 路线。教训：先确认硬件链路，再写应用代码。
2. **审批卡被状态顶掉**：一条命令批准后，`PostToolUse` 立刻上报 working，
   把屏幕上**下一条**审批卡刷掉，用户根本不知道还有审批在等。修复：审批期间只记账不下发；
   回归测试是用例 14。
3. **无人触碰却收到 deny**：空闲 D2/D3 读到 HIGH，但曾收到 deny；加 35 ms 稳定低电平
   去抖 + 松开重武装，12 秒审批卡保持测试无误拒。

### 0.5 三个“还没做完”（主动说，比被问出来强）

1. 最新 Clawd 静态画面的**真机观感**还在确认；长中文折行、缺字空心框还没完整实测。
2. 设计文档里标“待实测”的**性能数字**：状态刷新延迟、按钮响应、8 小时稳定性。
3. 还没做：多会话 FIFO 队列、外壳 3D 打印、按钮消息丢失后的 ack/重发、本地 Socket 认证。

### 0.6 三条红线

- ❌ 不要说“代码全是我写的，没用 AI”——这个项目本来就用 AI 辅助，被拆穿一次，后面全打折。
- ❌ 不要说“这个我全懂”——面试官最爱追问这种话。
- ❌ 不要沉默——不知道就说不知道，然后说出你会怎么查、怎么验证。

## 一、项目事实卡

> 这一节是**面试前必须核对**的。数字记错比不会更尴尬。
> 所有数字以 2026-10-27 的仓库状态为准；编译数字会随工具链/库版本略有浮动。

### 1.1 30 秒版（自我介绍里带一句）

> 我是 XXX，大一。平时用 AI 辅助写代码，老要切回终端看它干完没有，挺打断思路的。
> 所以我做了个小设备：一块屏幕加两个按钮，用一根 USB 线连电脑，AI 在忙什么、
> 要不要我批准，在桌面上直接就能看到、直接就能按。硬件的选型、接线和电脑端都是我自己做的，
> 代码在我的 GitHub 上。

### 1.2 2 分钟版（重点准备这个）

> 我平时用 AI 帮我写代码。用久了发现一个挺烦的事：AI 干活的时候你不知道它干完没有，
> 得反复切回终端看；它要是卡在等你确认一条命令上，你没看见，它就一直等着。
>
> 所以我做了 VibePet。它是一个巴掌大的小盒子，上面一块 1.77 寸的彩色屏和两个按钮，
> 用一根 USB 线连到电脑。AI 在忙、空闲、干完了、出错了，屏幕上都会实时显示；
> 需要你批准一条命令的时候，它会响三声、屏幕上弹出一张黄色卡片，把要执行的命令写在上面，
> 你按批准键或拒绝键，电脑那边立刻就能收到。
>
> 它分成三部分：电脑上有个常驻的小程序一直守着设备连接，还有个“接线员”接住 AI 那边发来的消息；
> 设备端是一块 Arduino UNO，负责驱动屏幕、扫描按钮、收发报文。硬件的选型和接线是我自己做的，
> 电脑端代码和固件也是在这个项目里从零写的。
>
> 现在电脑端四套测试 49 例、固件端离线测试 55 例，一共 104 例全过；设备已经烧进板子，
> Bash 审批的批准和拒绝都实测通过了。**还没做完的是最新画面的真机观感、长中文折行、
> 缺字框和性能数字**——这些是我接下来要补的。
>
> 这个项目让我第一次完整走了一遍“从想法到能演示的东西”的过程，也逼着我去搞懂了
> 串口通信、异步编程，还有“资源特别少的单片机该怎么写程序”这件事。

### 1.3 5 分钟版

在 2 分钟版的基础上，按这个顺序补：

1. **痛点讲具体**：举一个你真遇到的场景（“有次 AI 等我批一条删文件的命令，我在看别的窗口，
   它干等了十分钟”）。
2. **讲一个坑的过程**（0.4 里挑一个，用 STAR：现象 → 排查 → 发现 → 修复 → 学到什么）。
3. **讲一个取舍**：为什么按钮按下去屏幕立刻就变，而不等电脑回话——因为链路偶尔会卡，
   等它回话屏幕就僵在那儿了；代价是如果按钮消息丢了，设备会显示“已批准”但 daemon 超时拒绝，
   这是已知的乐观反馈问题。
4. **讲一个数字背后的故事**：比如 320 字节、35 ms、5 秒看门狗，任选一个。
5. **收尾讲学到什么 + 下一步**。

### 1.5 七种状态

| 状态值 | 屏幕标题 | 颜色 | Clawd 表情 / 道具 | 触发方式 |
|---|---|---|---|---|
| `idle` | IDLE | 白 | 方块眼 | `SessionStart` / `SessionEnd` / 恢复 |
| `working` | WORKING | 绿 | 半睁眼 + 笔记本电脑 | `UserPromptSubmit` / `PostToolUse` 成功 / `SubagentStop` / `PreCompact` |
| `needs_you` | APPROVE? | 黄 | 睁大眼 + 感叹号 + 双线外框 | `approval_request`（不是 `state`） |
| `done` | DONE | 青 | 笑眼 + 对勾与闪光点 | `Stop`，3 秒后自动回 IDLE |
| `error` | ERROR | 红 | 叉眼 + 乌云与雨点 | `PostToolUse` 失败 |
| `heartbeat_lost` | LOST | 橙 | 闭眼 + 断线符号 | 设备看门狗（5 秒无任何消息） |
| `interactive` | CHECK PC | 蓝紫 | 方块眼 + 小显示器 | `AskUserQuestion` / `ExitPlanMode` |

> 注意：`needs_you` **不能**由 `state` 消息触发；设备只认 `approval_request`。
> 这是串口探针 `/state needs_you` 会被忽略的原因，调试时要用 `/approval`。

### 1.6 三层架构与一条数据流

```
Claude Code / Codex
   │ Hook 事件（stdin JSON）
   ▼
hook_client.py / codex_hook.py     短生命周期：每次 Hook 起一个进程
   │ 本地 TCP 127.0.0.1:8765（JSON 一行）
   ▼
bridge_daemon.py                    常驻：独占串口 / 心跳 / request_id / 审批等待
   │ USB 串口 115200，JSON Lines
   ▼
Arduino UNO R3 固件                 收行 → 解析 → 画屏 / 扫按钮 / 看门狗
```

**一次审批的完整往返**：

1. Claude Code 触发 `PreToolUse`（Bash）或 `PermissionRequest`（非 Bash）；
2. `hook_client.py` 读 stdin，把事件原样转给 daemon，然后**阻塞**等；
3. daemon 生成 8 个十六进制字符的 `request_id`，发 `approval_request`（tool + summary）；
4. 设备存下 `request_id`，画 `APPROVE?`，响三声，LED 亮；
5. 用户按 D2 / D3；设备回传带同一个 `request_id` 的 `button`；
6. daemon 校验 `request_id`，把 approve / deny 返回给客户端；
7. 客户端按事件格式输出决策 JSON；设备本地已先切画面（已批准 / 已拒绝）。

### 1.8 已经验证 vs 还没验证

**已经验证（可以理直气壮说）**

**还没验证 / 别说过头**

- 最新 Clawd 静态画面的真机观感。
- 长中文折行、缺字空心框的完整实测。

- `PermissionRequest` 的拒绝路径、更多非 Bash 工具类型。

- daemon 缺席时状态上报仍有约 1 秒等待（实测约 1.1 秒）；虽然静默，但会叠加到每次工具调用上，下一步可以改成更短的连接探测。

## 二、把技术讲成人话

> 这一节是**讲给不懂的人听**时的工具。面试官懂技术，可能用不上——
> 但“能不能把复杂的东西讲简单”，本身就是他考察你的一种方式。
> 而且现场未必只有他一个人。

**核心：讲类比，不讲名词。**

### 2.1 六个类比

| 技术点 | 类比 |
|---|---|
| 状态显示 | **厨房的出菜铃**：厨师（AI）做好了会响铃，你在外面忙就行，不用一直站在厨房门口盯 |
| 物理审批 | **手机支付确认**：不是不信任，而是重要操作要你亲手点一下同意 |
| 行重组 | **快递分拣**：一条消息可能分几个包裹到，得先按单号拼齐，不能拿到半截就拆 |
| 心跳/看门狗 | **监护仪**：每秒“滴”一下，5 秒没动静就报警，而不是让屏幕停在最后一个假状态 |
| request_id | **取餐号**：按钮回传必须带当前号码，过期的号不认，防止“迟到的手指”批准下一条 |
| UTF-8 截断 | **切字符串不能切在汉字中间**：一个汉字占 3 个字节，切一半就成乱码 |

### 2.2 一句话解释 15 个名词

| 名词 | 一句话 |
|---|---|
| Hook | AI 软件在“要干活/干完活”时主动喊一声的机制 |
| daemon | 常驻后台、一直守着设备的程序 |
| 串口 | 一根线按位收发字节的通道；UNO 的 USB 口在电脑上就是一个 COM 口 |
| 115200 8N1 | 每秒约 115200 位，8 数据位、无校验、1 停止位 |
| JSON Lines | 一条消息一行 JSON，按 `\n` 切分 |
| request_id | 这次审批的取餐号，按钮必须原样带回 |
| 看门狗 | 一段时间没收到消息就判定失联的计时器 |
| 去抖 | 按钮机械触点会抖，连续稳定一段时间才算按下 |
| 非阻塞 | 不站在原地等，而是每轮循环推进一点点 |
| PROGMEM | 把常量放在 Flash 里，不占只有 2 KB 的 RAM |
| RGB565 | 用 16 位表示一个像素（5+6+5），比 24 位省 1/3 |
| framebuffer | 整屏像素缓存；128×160×2 = 40 KB，UNO 装不下，所以直接画 |
| UTF-8 | 汉字通常占 3 字节；截断必须落在字符边界 |
| asyncio | Python 的异步并发：一个线程里交替推进多个等待任务 |
| fail-closed | 拿不准就拒绝，而不是放行 |

### 2.3 用一张图讲完整流程

```
你敲一条命令
   ↓
Claude Code：要不要先问一下？ → 触发 Hook
   ↓
hook_client：把事件转给 daemon，然后卡住等你
   ↓
daemon：生成取餐号，发到设备
   ↓
设备：屏幕变黄、响三声、LED 亮；你按按钮
   ↓
设备：把“批准/拒绝 + 取餐号”发回电脑
   ↓
daemon：号码对得上 → 告诉 hook_client
   ↓
Claude Code：继续执行 / 不执行
```

### 2.4 三个“为什么这事不容易”（说人话版）

| 难点 | 说人话的版本 |
|---|---|
| 连接不能随用随开 | 那根线对应的串口，同一时刻只能被一个程序占着；而且一打开，板子还会自己重启一次。所以必须让一个程序一直守着，不能每次用的时候现开——这就是为什么分成两个程序 |
| 屏幕上显示中文 | 小屏幕的驱动库默认只有英文字母，完整中文点阵字库 200 KB，比芯片全部存储还大六倍。所以我写了个工具，从完整字库里裁出设备真正用得上的 394 个字，压到 9 KB 塞进去 |
| 消息会被切碎 | 一条消息可能分几次到达，得自己把碎片拼回一整条；还不能把汉字从中间切断，截断要按 UTF-8 边界退 |
| 屏幕点不亮不一定是代码问题 | UNO 的 3.3V 引脚官方只给 50 mA，带背光的屏经常超；电供不上就是白屏。这类“代码看着没错、硬件不给力”的坑，只能靠量电压、换供电去排除 |

### A 类 · 项目与动机（12 题）

**A1. 这东西具体能干什么？** ⭐
A：三件事——显示 AI 的工作状态；需要批准时提醒你并把命令摘要显示出来；让你按物理按钮批准或拒绝。设备通过 USB 线供电和通信。

**A2. 为什么做这个？** ⭐
A：我自己用 AI 写代码时，老要切回终端看它干完没有；它卡在等我批命令时，我没看见，它就一直等。我想要一个“眼睛扫一下就知道、手按一下就能批”的东西。另一个原因是我本来就想学硬件。

**A3. 有什么实际用处？做这个值吗？** ⭐
A：用处就是“不用盯终端”，尤其适合命令审批频繁、又经常切窗口的人。老实说这是个偏个人的需求，不是所有人需要；但做它的过程里学到的东西比结果更值。

**A4. 为什么不做成手机 App？**
A：App 也能做，但得解锁手机、找到 App、打开，反而比切回终端还麻烦。我想要的是“眼睛扫一下就知道”。另外我本来就想学硬件，这是个好机会。

**A5. 为什么不做成桌面小组件/网页？**
A：桌面小组件能显示状态，但没有“物理按钮”的仪式感和盲操感；审批还是得用鼠标点。我的目标是把“看”和“批”都从键盘/鼠标上挪开。

**A6. 目标用户是谁？**
A：主要是我自己这类“长时间用 AI 写代码、又经常被审批打断”的开发者。不是大众产品；如果要做大，得先解决多会话、外壳、安装门槛这些问题。

**A7. 做了多久？** ⭐
A：大概 6 周，断断续续的课余时间；仓库里 56 次提交。中间有一段时间卡在屏幕上，实际写代码的时间没有 6 周全花在功能上。

**A8. 一个人做的吗？** ⭐
A：是一个人做的。需求、选型、接线、调试、验收都是我；开发中用了 AI 编程助手，关键设计决定我能解释。如果是一个小队，我会把硬件、电脑端、固件分三块并行，最后一起联调。

**A9. 最难的地方是哪里？** ⭐
A：最难的不是写功能，是**定位“屏幕为什么不亮”**。代码看着没错，换库、换引脚都没用，最后判断是硬件链路的问题，换到有已验证例程的 UNO 路线。第二难的是“审批卡被状态顶掉”这种只在真实使用中才暴露的时序 bug。

**A10. 最有成就感的地方？**
A：设备第一次按批准、终端里的命令真的放行的那一刻。还有把“审批卡被顶掉”这个 bug 用回归测试锁住的时候——那说明我不只是让它跑起来，还让它不容易坏。

**A11. 如果重做一次，会改什么？**
A：三件事：① 先用“已知能点亮”的显示路线做最小验证，再写应用；② 固件拆成几个模块，不要一个 984 行的 `.ino`；③ 一开始就把测试和文档当成交付物，而不是最后补。

**A12. 这个项目最大的不足？** ⭐
A：最新画面的真机观感、长中文折行、缺字框、性能数字还没完整验证；功能上是单槽审批、没有多会话队列、没有外壳；可靠性上按钮消息丢失时设备会乐观显示“已批准”，而 daemon 可能超时拒绝。这些我都知道，也知道下一步怎么补。

### B 类 · 硬件与电气（20 题）

**B1. 为什么选 Arduino UNO R3？** ⭐
A：三个原因：① USB 口本身就是串口链路，不需要无线模块；② 5V 逻辑、引脚耐操，面包板接线不容易坏；③ 仓库里有能编译、能点亮的 UNO + ST7735 例程，显示链路是已知的。代价是资源只有 32 KB Flash / 2 KB RAM。

**B2. 为什么不用 ESP32？** ⭐
A：最初就是 ESP32 + BLE。蓝牙链路本身调通了，但同一块屏一直“背光亮、无画面”，换库、换引脚、换 SPI 速度都没解决。我判断继续耗下去不划算，换到有已验证显示例程的 UNO。不是 ESP32 不好，是那条硬件组合我查不动了。

**B3. 为什么不用树莓派/STM32？**
A：树莓派是完整 Linux，成本、功耗、启动时间都大，而且我想练的是“资源受限”的嵌入式。STM32 我也碰过，但显示链路同样要重新验证；UNO 的优势是生态和例程最全。选型不是选最强，是选我能在有限时间里做完的。

**B4. 为什么从无线改有线？这不是退步吗？** ⭐
A：功能上少了个“无线”，但换来的是插上就能用：不用配对、不用装蓝牙驱动、不用管信号。更重要的是我把问题从“屏幕为什么不亮”（查不出来）换成了“在 32 KB / 2 KB 里把中文显示做出来”（具体、能一步步做）。遇到查不动的死路时换方案，我觉得比硬耗着强。

**B5. 屏幕是什么型号？分辨率？接口？**
A：1.77 英寸 ST7735S TFT，128×160，SPI 接口，RGB565 色深。竖屏用 `setRotation(0)`；如果画面倒置就改 `setRotation(2)`。

**B6. 为什么用 SPI 不用 I2C？**
A：128×160 彩色屏的数据量大，I2C 速率低，刷屏会明显慢；SPI 快得多，Adafruit 的 ST7735 库也是 SPI 的。代价是多几根线，但接线一次就好。

**B7. 屏幕怎么接线？引脚为什么这样分？** ⭐
A：CS=D10、DC/A0=D9、RES=D8、SDA/MOSI=D11、SCK=D13、VCC/LEDA=3.3V、GND=GND。D11/D13 是 UNO 硬件 SPI 固定引脚，改不了；CS/DC/RES 可以挑，这里和 `tfttest_uno` 例程保持一致，方便对照。

**B8. 3.3V 引脚只有 50 mA，怎么办？** ⭐
A：这是白屏的头号嫌疑。UNO R3 的 3.3V 由板载 LDO 提供，官方标称 50 mA；带背光的 1.77" 模块经常超。点不亮时先把模块 VCC 改接 5V（仅限模块自带 LDO 的型号），背光 LEDA 可留 3.3V 或一并改 5V，看模块有没有限流电阻。

**B9. UNO 是 5V 逻辑，屏幕是 3.3V，会不会烧？**
A：多数 1.77" 模块的输入带串联电阻，可以直接接；如果是纯 3.3V 输入且接上发热/显示异常，就要加电平转换或串 100–470 Ω 电阻。我的模块按例程直连，实测正常。

**B10. 屏幕白屏怎么排查？** ⭐
A：按顺序：① 背光有没有亮？不亮查 VCC/GND/LEDA；② 背光亮但没画面，先怀疑供电不足，改 5V；③ 还不行换初始化序列 `INITR_BLACKTAB` → `GREENTAB` → `REDTAB`；④ 最后才怀疑模块坏了。核心原则是**先排除供电和接线，再怀疑代码**。

**B11. 花屏、偏色、画面偏一格呢？**
A：这不是接线问题，是初始化序列不匹配。换 `INITR_BLACKTAB` / `INITR_GREENTAB` / `INITR_REDTAB` 逐个试。

**B12. 为什么 D0/D1 不能接外设？** ⭐
A：D0/D1 是 UNO 的硬件串口 RX/TX，既是和电脑的数据链路，也是烧录口。接上任何外设，轻则通信受干扰，重则电脑认不到设备、烧录失败。

**B13. 按钮怎么接？为什么用 INPUT_PULLUP？** ⭐
A：按钮一端接 D2（批准）/ D3（拒绝），另一端接 GND；引脚设 `INPUT_PULLUP`，不按是高电平，按下是低电平。用内部上拉省了外部电阻，接线简单；低电平有效也方便做去抖。

**B14. 蜂鸣器有源和无源有什么区别？** ⭐
A：有源内部自带振荡源，给个电平就响；无源内部没有振荡源，必须给方波，给直流只会“咔哒”一声。本项目用无源，`tone()` 输出 2700 Hz 方波；如果装的是有源，把固件里的 `BUZZER_ACTIVE` 改成 1。

**B15. 为什么蜂鸣器接 D4、LED 接 D5？**
A：这两个是空闲引脚，避开了 SPI 和串口。`tone()` 在 AVR 上用 Timer2，会影响 D3/D11 的 PWM，但 D3 是按钮输入、D11 是 SPI MOSI，都不当 PWM 用，所以不冲突。D13 的板载 LED 和 SCK 共用，不能当状态灯。

**B16. 为什么 D13 的板载 LED 一直闪？**
A：D13 是硬件 SPI 的 SCK，屏幕刷新时时钟线在翻转，板载 LED 就跟着闪。这是正常现象，不是故障；也正因为如此，状态灯不能用 D13。

**B17. 供电和功耗大概多少？**
A：整机由 USB 5V 供电，UNO 本身 + 屏幕背光 + 蜂鸣器，具体电流我没逐项测；背光是主要负载。设备不支持电池，因为数据链路就是这根线，独立供电没有意义。

**B18. 外壳、尺寸、成本？**
A：外壳还没做，现在是 UNO + 面包板/杜邦线。BOM 目标 ≤ ¥100：UNO 约 30–60、屏幕约 15、按钮约 2、蜂鸣器约 5、LED 约 1、线材约 10；具体采购价还没逐项核实。尺寸等外壳做了再定。

**B19. 如果按钮坏了一个怎么办？**
A：当前固件把 D2 当批准、D3 当拒绝，坏一个就少一个决策。临时可以交换两个按钮的杜邦线来确认极性；长期可以在固件里加“长按批准/短按拒绝”或第三个按钮，但那就改变了交互，需要重新设计去抖和 UI。

**B20. 如果屏幕坏了，设备还能用吗？**
A：审批链路本身不依赖屏幕绘制：daemon 仍然能发请求、设备仍然能收按钮、回传决策；但你没法看摘要，只能盲按，这很危险。所以屏幕坏了应该停用审批，而不是“凑合用”。可以加一个“屏幕自检失败就不接受审批”的策略，当前没做。

### C 类 · 嵌入式与固件（30 题）

**C1. 主循环怎么跑？** ⭐
A：`loop()` 里五件事：① `pumpSerial()` 把串口字节搬进行缓冲；② `while (rxLine.ready)` 处理完整行；③ `checkWatchdog()` 判断失联、控制 LED；④ `scanButtons()` 扫按钮、去抖、回传；⑤ `beepService()` 推进蜂鸣器节奏；最后 `delay(2)`。没有 RTOS、没有中断回调，单任务协作式。

**C2. 为什么不用 RTOS/中断？** ⭐
A：UNO 只有 2 KB RAM，FreeRTOS 的任务栈和调度器开销不划算；而且这个项目的并发很简单：收串口、扫按钮、响蜂鸣器，用 `millis()` 状态机就够了。中断只保留硬件 USART 收字节和 `tone()` 的 Timer2，其他都在主循环里做，避免共享状态的锁问题。

**C3. “连续阻塞 ≤ 3 ms”怎么来的？** ⭐
A：115200 波特率约 11.5 字节/ms，3 ms 约 35 字节。UNO 默认串口接收缓冲 64 字节，约 5.5 ms 就满；提升到 256 字节约 22 ms。3 ms 是一个保守预算：既给缓冲留余量，也保证屏幕绘制不会让串口饿死。整屏绘制要切片，每片之间 `pumpSerial()`。

**C4. 串口接收缓冲为什么设 256？**
A：默认 64 字节，一条审批请求最长 320 字节；虽然 `pumpSerial()` 会持续把字节搬走，但突发时 64 字节余量太小。`-DSERIAL_RX_BUFFER_SIZE=256` 把硬件环形缓冲提到 256，约 22 ms 容错。注意用 Arduino IDE 编译时是 64 字节，靠 3 ms 纪律也够用。

**C5. 整屏绘制怎么不丢串口？** ⭐
A：所有大面积绘制都切片：`fillScreenSliced()` 每次填 8 行（约 2.5 ms），片与片之间 `pumpSerial()`；`drawGlyph()` 每画完一个字 `pumpSerial()`；`drawBodyText()` 每画完一行 `pumpSerial()`。这样任何一段连续阻塞都不超过 3 ms。

**C6. 为什么没有 framebuffer？**
A：128×160×2 字节 = 40,960 字节，UNO 只有 2,048 字节 SRAM，装不下。所以直接用 Adafruit 的绘图原语往屏幕写，状态切换时整屏重绘一次。代价是重绘期间会闪一下，但静态画面可以接受。

**C7. RGB565 是什么？为什么不用 RGB888？**
A：RGB565 用 5 位红、6 位绿、5 位蓝，共 16 位表示一个像素；RGB888 要 24 位。565 省 1/3 带宽和存储，颜色对状态显示够用。屏幕和 Adafruit 库都按 16 位颜色工作。

**C8. 中文怎么显示？** ⭐
A：自制 12×13 点阵子集字库。每个字 20 字节位图 + 2 字节码点 + 1 字节步进宽，约 23 字节。运行时按码点二分查找字形，逐行取 12 位掩码，按位画到屏幕。ASCII 和汉字走同一张表、同一套绘制路径。

**C9. 字库怎么裁？为什么是 394 字？** ⭐
A：`tools/gen_cn_font.py` 从本机 U8g2 的 `wqy12_t_gb2312`（202690 字节、7477 个字形）里，按 `tools/cn_charset.txt` 裁出设备可见文案、开发词汇和通用高频字，共 394 字（95 ASCII + 299 汉字），约 9.1 KB。再多了 Flash 装不下；现在只剩约 1.3 KB，按每字 23 字节算上限约 59 个字，实际建议按 50 个左右规划。

**C10. 12×13、20 字节怎么算？**
A：13 行 × 12 位 = 156 位，向上取整到 160 位 = 20 字节。每行 12 位在字节流里连续打包，任意一行最多跨 2 个字节。

**C11. 取行时位序是什么？踩过什么坑？** 🔍
A：**返回值的第 c 位就是第 c 列，位 0 是最左**。曾经写成 `0x800 >> c`，读到的是镜像列，整个字左右翻转。这个约定写在 `cn_font.h` 和 `test_proto.cpp` 里，有回归测试。

**C12. 字形索引为什么必须用 16 位？** 🔍
A：字库有 394 个字，超过 255。曾经把索引参数写成 `uint8_t`，索引 ≥ 256 的字被截断成别的字，屏幕上表现为“有的汉字变成英文字母”。现在参数、偏移一律用 16 位以上，`test_proto.cpp` 有对应测试。

**C13. 遇到没收录的字怎么办？**
A：画一个 12×13 的空心方框。它比问号更明确：问号本身可能是一个真实字符，空心框一眼就能看出“这个字缺了”。把字加进 `tools/cn_charset.txt`，重新生成 `cn_font.h`，再烧一次固件。

**C14. 中文折行怎么保证不切碎汉字？** ⭐
A：折行按“字”而不是按“字节”：`utf8Next()` 读出一个完整 UTF-8 字符，`glyphAdvance()` 取宽度，累加到行宽上限。截断也是按字符边界退，不会切在 3 字节汉字的中间。

**C15. 正文最多几行？为什么？**
A：气泡内最多 4 行，行高 13 px，气泡高 60 px，留内边距刚好放 4 行；每行约 9 个汉字（内部宽 108 px / 12 px）。超出用 `..` 收尾，不缩小字号。

**C16. 标题为什么用内置字体放大？**
A：标题都是英文大写（IDLE / WORKING / APPROVE? 等），Adafruit 内置 5×7 字体放大 2 倍就够醒目，省下一套大号中文字库。正文才用 12px 子集字库。

**C17. 按钮去抖怎么实现？** ⭐
A：每个按钮独立记录“低电平开始时间”；`digitalRead()==LOW` 连续稳定 35 ms 才算有效按下；按下后锁存，直到松开才重新武装。这样毛刺不会误触发，长按也不会把下一张审批卡一起按掉。

**C18. 为什么是 35 ms？长按会怎样？**
A：机械按钮的抖动通常几毫秒到十几毫秒，35 ms 足够稳，人感觉不到延迟。按下后锁存到松开，所以长按只算一次；松开后才允许下一次决策。

**C19. 两个按钮同时按会怎样？**
A：`scanButtons()` 先处理批准，再处理拒绝。批准有效时会清空 `request_id`，拒绝那一轮看到空 id 就不再发。所以同时按的结果是“批准优先”。这个优先级没有写在需求里，是一个可以改进的点（比如定义为拒绝优先，更安全）。

**C20. 蜂鸣器怎么做到非阻塞？** ⭐
A：`beepStart(times, on_ms, off_ms)` 只设定“响几声、每声多久、间隔多久”；`beepService()` 每轮循环用 `millis()` 判断该开还是该关，从不 `delay()`。这样响的时候主循环还在收串口。

**C21. 为什么不能用 delay 等蜂鸣器响完？**
A：120 ms 的 `delay` 在 115200 下会积压约 1380 字节，即使 256 字节缓冲也早溢出了；丢的可能正是下一条审批请求。所以蜂鸣器必须做成状态机。

**C22. 看门狗怎么实现？** ⭐
A：每次收到**任何**一条合法消息都刷新 `lastHeartbeat`；主循环里判断 `millis() - lastHeartbeat > 5000`，超时就切 `LOST`。不只是心跳算保活，状态消息也算——只要电脑还在说话，就不该误报失联。

**C23. LOST 恢复策略是什么？** ⭐
A：进入 LOST 时清空 `request_id`，失联期间按键不回传，画面不画正文。恢复时回到 `lastValidState`；如果那是 `needs_you` 或 `interactive`，就回 `IDLE` 并清掉旧文案——那张卡可能已经过期，不能骗用户按一个无效按钮。

**C24. DONE 为什么 3 秒后回 IDLE？**
A：否则屏幕会一直停在 DONE，直到下一次会话事件；用户可能以为任务还在跑。3 秒足够看到“完成”，又不会长期占屏。期间如果收到新状态，`setState()` 会刷新时间戳，不会误回退。

**C25. 七态状态机怎么组织？**
A：`enum PetState { ST_IDLE, ST_WORKING, ST_NEEDS_YOU, ST_DONE, ST_ERROR, ST_LOST, ST_INTERACTIVE }`；`setState()` 是唯一入口，负责记录 `lastValidState`、刷新时间戳、整屏重绘；绘制用 `switch` 分派。没有复杂的层次状态机，因为状态少、转换简单。

**C26. 为什么用 enum + switch，不用函数指针/状态表？**
A：七种状态、转换不复杂，`switch` 最直白，编译器也能优化成跳转表。函数指针会增加间接层和 RAM/Flash 开销，对这个规模不划算。

**C27. 内存都花在哪？栈够吗？**
A：SRAM 1299 字节：Serial 349、行缓冲 324、msgBuf 161、其余（Adafruit 对象、request_id、时间戳、按键状态）465。剩 749 字节给栈。最深路径是 `fillRect → writeColor`，没有大局部数组；`drawGlyph` 里一行像素只有 24 字节。

**C28. 有没有动态内存/递归风险？** 🔍
A：没有 `malloc`/`new`/`String`，全部静态缓冲。递归有一处：`utf8Next()` 遇到非法首字节会递归跳过。正常 daemon 发的是合法 UTF-8，不会触发；理论上如果有人灌一长串非法字节，递归可能压栈。这是一个可以改成循环的地方，我记在待办里。

**C29. Flash 只剩 1.3 KB，怎么办？**
A：按影响从小到大裁：字集 394 → 300 → 250（每减 100 字约省 2.3 KB）→ 砍状态道具/状态灯 → 砍多行折行 → 标题改用自制字体、丢掉 Adafruit 内置字体（省约 2.5 KB）→ 最后才考虑自绘图元替掉 Adafruit 图形栈。

**C30. 如果加一个新状态/新动画怎么做？**
A：加状态：`enum` 加一项、`stateColor()` 加颜色、`renderState()` 加标题/表情/道具、`dispatchLine()` 加触发条件、`checkWatchdog()`/恢复逻辑确认、文档和测试同步。加动画要先看 Flash；当前只剩 1.3 KB，逐帧动画基本放不下，优先做静态表情/道具。

### D 类 · 通信协议（22 题）

**D1. 为什么用 JSON Lines？** ⭐
A：一条消息一行、纯文本、人能读、串口探针能直接敲；跨语言、跨平台都容易接。开销对这个带宽不是问题（一行最多 320 字节）。

**D2. 为什么不用二进制协议？**
A：二进制更省，但调试成本高：出问题时你没法用串口监视器直接看懂。这个项目的数据量很小，JSON 的可读性更值。真到了带宽/延迟瓶颈再换。

**D3. 为什么整行限制 320 字节？** ⭐
A：审批请求骨架约 66 字节 + request_id 8 + tool 24 + summary 160 = 最坏 258 字节。如果上限收到 256，带长工具名的请求会被设备整条静默丢弃——屏幕空白、120 秒后超时拒绝，电脑端还不知道。320 留出余量。

**D4. 最坏情况怎么算？**
A：`{"type":"approval_request","request_id":"…","tool":"…","summary":"…"}` 的骨架约 66 字节；request_id 8；tool 24；summary 160；合计约 258。320 - 258 = 62 字节余量，给字段名/转义留空间。

**D5. 为什么 summary 160、tool 24？**
A：summary 160 字节约 53 个汉字，是协议上限；屏幕只显示约 36 个汉字（4 行 × 9），超出的部分由固件用 `..` 收尾。tool 24 字节是为了守住整行预算，长工具名（如 `mcp__github__create_issue`）会被截断，但不会把整行顶爆。

**D6. UTF-8 截断怎么做？** ⭐
A：`clamp_bytes()` 先按字节上限截，然后往回退到 UTF-8 字符边界：如果截断点落在续接字节（`10xxxxxx`）上，就继续往前退，直到退到首字节。这样不会切出半个汉字。固件端的 `VpSink` 写满时也做同样的退让。

**D7. 串口分片怎么重组？** ⭐
A：按字节攒进行缓冲，遇到 `\n` 才算一条完整行；攒的时候**不先解码**，因为一个汉字的 3 个字节可能被拆在两次读取里，先解码会乱码。切分完再按 UTF-8 解码。

**D8. 超长行怎么处理？**
A：`vpLineFeed()` 发现缓冲到 `VP_LINE_MAX - 1` 还没见到 `\n`，就进入 `dropping` 状态，一路丢到行尾再复位；绝不把半截行当消息处理，也不让后面的行受影响。

**D9. 心跳为什么 1 秒、看门狗 5 秒？** ⭐
A：1 秒一次意味着连续丢 4 个心跳都不会误判；5 秒是“人能接受的最长假状态时间”。心跳同时是 daemon 的链路探针：串口拔掉后 Windows 不一定立刻报错，只有写失败才能发现，每秒写一次让掉线最多 1 秒暴露。

**D10. 为什么任何消息都算保活，不只心跳？**
A：只要电脑还在发合法消息，链路就是通的；状态消息比心跳更频繁。只认心跳会在“心跳丢了但状态还在”时误报 LOST。反过来，任何合法消息都刷新计时器，更稳。

**D11. request_id 是干什么的？** ⭐
A：每次审批生成一个 8 个十六进制字符的编号（UUID 前 8 位，32 位），设备回传按钮时必须原样带回；daemon 只接受当前等待中的那个。它解决“迟到按钮”问题。

**D12. 8 位够吗？会碰撞吗？** 🔍
A：32 位，单槽同时只有一个待审批请求；碰撞只在“旧按钮的 id 恰好等于新请求的 id”时才有影响，概率约 1/2^32。它不是安全令牌，只是关联编号；真要防伪造得加签名/认证，那是另一个威胁模型。

**D13. 不加 request_id 会出什么问题？** ⭐
A：“迟到按钮”：某次审批已经超时作废，用户过一会儿才按下去，这个按钮会误批准下一次请求——等于你批准了一条自己根本没看过的命令。

**D14. 重连时审批卡怎么处理？**
A：`resend_current()` 如果发现还有审批在等，就重发审批卡，并**沿用原 request_id**，这样设备回传的按钮仍然有效；如果没在等，就重发最后一条 state。

**D15. hello 是干什么的？** ⭐
A：设备每次复位（上电、按复位键、打开串口导致的自动复位、重新烧录）后发 `{"type":"hello","fw":"uno/1.0"}`。复位不会断开串口，光靠“掉线重连”发现不了，屏幕会停在开机画面；daemon 收到 hello 就补发当前画面。

**D16. 为什么打开串口会让板子复位？**
A：USB 转串口芯片在端口打开时会给 ATmega328P 的 RESET 一个脉冲，板子重新跑 bootloader（约 1.5–2 秒）。这不是故障，是 Arduino 的自动复位设计。

**D17. boot grace 为什么 2 秒？**
A：这 2 秒里 bootloader 会把我们发的字节当 STK500 烧录命令吃掉；如果立刻发状态，屏幕可能收不到。`connected` 在 boot grace 期间返回 False，等过了再补发当前画面。

**D18. 为什么用本地 TCP，不用管道/共享内存？**
A：TCP 跨平台、标准库直接支持、调试方便（`status` 查询、`--no-device` 注入按钮）；127.0.0.1 只在本机，不经过网卡。管道在 Windows 上跨语言/跨进程的兼容性更麻烦。

**D19. Socket 半关闭（SHUT_WR）是干什么的？** 🔍
A：daemon 用 `reader.read(4096)` 读请求，`read()` 要读到 EOF 才返回；客户端发完请求后必须 `shutdown(SHUT_WR)` 告诉对方“我说完了”，否则两边互等，审批卡到超时才解开。消息末尾的 `\n` 是给 `readline()` 实现留的余地。

**D20. 协议怎么扩展一个新消息？**
A：两端同步改：电脑端发新 `type`，固件 `dispatchLine()` 加分支，`docs` 和测试同步；整行仍要 ≤320 字节，字段仍要按 UTF-8 截断。改协议必须跑 `test_proto.cpp` 和两套 smoke test。

**D21. 怎么调试协议？**
A：三层：① `tools/serial_probe.py` 直接发 JSON，绕开电脑端；② daemon `-v` 看每条收发；③ `test_proto.cpp` 离线测解析内核和字库取行。先确认“设备能不能听懂”，再查“上层逻辑对不对”。

**D22. 设备回传非法 JSON 怎么办？**
A：daemon 用 `json.loads()` 包在 try 里，解析失败只记日志、丢弃这一行；不是对象的 JSON 也丢弃。绝不让一条坏消息把进程带崩。固件端同理：解析失败保留旧状态，不显示半截内容。

### E 类 · 电脑端 Python 与异步（20 题）

**E1. 为什么用 Python？**
A：开发快、标准库够用（socket/asyncio/json）、跨平台；这个项目不是性能瓶颈。第三方依赖只有 pyserial，`hook_client.py` 纯标准库，装机门槛低。

**E2. 为什么分两个程序？** ⭐
A：串口独占，而且一打开板子就复位；Hook 每次都会新起一个短命进程，承受不了“现开现关”。常驻 daemon 抱着串口，短命客户端只走本地 Socket，一次往返，daemon 不在时安全降级。

**E3. daemon 怎么管串口？**
A：`SerialTransport` 打开端口、等 boot grace、起一个后台线程读；读到的字节按 `\n` 拼行，再用 `call_soon_threadsafe()` 把整行送回 asyncio 事件循环。所有 `Bridge` 的 asyncio 原语只在事件循环线程上碰。

**E4. 为什么用后台线程读串口？**
A：pyserial 的 `read()` 是阻塞的，直接在事件循环里读会卡住心跳、Socket、审批等待。放到线程里读，事件循环继续跑；线程只负责收字节和拼行，不做业务。

**E5. call_soon_threadsafe 干什么？**
A：把“后台线程收到的整行”安全地交给事件循环线程处理。asyncio 的 Event/Lock 不是线程安全的，不能在线程里直接 set；`call_soon_threadsafe` 是官方提供的跨线程投递方式。

**E6. asyncio 在这里怎么并发？**
A：心跳协程每秒发一次；本地 Socket server 接客户端；审批协程 `await` 按钮事件；连接协程负责重连。它们在一个事件循环里交替推进，不需要多线程共享状态。

**E7. 心跳和审批等待怎么同时进行？**
A：`wait_for_button()` 是 `await asyncio.wait_for(self._button_event.wait(), timeout)`；等待期间事件循环可以去跑心跳、Socket、读串口。按钮到达时 `_on_device_line()` 调 `set()` 唤醒。

**E8. 单槽审批怎么实现？**
A：`_approval_lock = asyncio.Lock()`；`handle_approval()` 用 `async with` 包住整个流程，第二个请求会排队等第一个走完。槽里放 `_pending_request_id`，只接受匹配的按钮。

**E9. 为什么有两把锁？会死锁吗？**
A：`_approval_lock` 管“一次只审批一个”，`_send_lock` 管“所有会改屏幕内容的发送串行化”，避免 `_state_dirty` 的读改写交错。嵌套顺序固定为 `_approval_lock → _send_lock`，没有反向路径，不会死锁。

**E10. `_last_state` / `_state_dirty` 是干什么的？** ⭐
A：`_last_state` 是“设备应该显示的内容”的账本，用来去重（PostToolUse 会反复报同一个 working，不去重屏幕会闪）；`_state_dirty` 表示“账本可能和屏幕不一致”（发送失败、屏幕被审批卡占据、刚重连），重连时 `resend_current()` 靠它无条件补发。

**E11. 审批进行中为什么不下发状态？** ⭐
A：真实 bug：一条命令批准后，`PostToolUse` 立刻上报 working，把屏幕上**下一条**审批卡刷掉，用户看到 WORKING，不知道还有审批在等，那条只能静默超时被拒。现在审批期间只记账不下发，`_state_dirty` 保持 True，审批结束后再补发。

**E12. 重连补发怎么知道该发什么？**
A：如果 `_pending_approval` 非空，重发审批卡（沿用原 request_id）；否则把 `_last_state` 重发一遍。重连时屏幕实际显示什么不确定，所以先置 `_state_dirty` 绕过去重。

**E13. 端口自动发现怎么打分？**
A：`discover_port()` 给每个串口打分：官方 Arduino VID/PID 3 分；描述里有 “arduino”/“uno” 2 分；常见 USB 串口芯片（CH340/FT232/CP2102）1 分；同分按端口名排序，保证每次选同一个。也可以用 `--serial-port` 手动指定。

**E14. 端口被占用怎么处理？**
A：打开失败只记日志、返回 False，`connection_loop()` 每 2 秒重试；不会崩，也不会静默假装成功。常见占用者：Arduino IDE 串口监视器、另一个 daemon、串口助手。

**E15. Windows 编码踩过什么坑？**
A：中文 Windows 的 Python 文本流默认 GBK，写入非 GBK 字符会抛 `UnicodeEncodeError`，Hook 进程会崩。`hook_client.py` 把 stderr reconfigure 成 UTF-8，stdout 用 `sys.stdout.buffer` 直接写 UTF-8 字节；新增脚本沿用这个模式。

**E16. 为什么 stdout 只能输出 Hook JSON？** ⭐
A：Claude Code 把 stdout 当决策解析，混进一句调试日志它就读不懂，审批链路直接断。所以所有日志走 stderr，只有 `emit_decision()` 碰 stdout；状态事件 stdout 必须零字节。

**E17. 150 / 130 / 120 秒为什么这样分层？** ⭐
A：Hook 150 > 客户端 130 > daemon 120。让 daemon 先演“超时降级为拒绝”，客户端多等 10 秒兜底，外部 Hook 最后才杀。这样不会出现“客户端先放弃、daemon 还傻等、屏幕留着作废卡片”。

**E18. 状态上报失败为什么静默？**
A：状态上报挂在每一次工具调用后面，为它多等一秒就是拖慢 Claude Code；屏幕只是锦上添花。失败只写 debug 日志（要 `VIBEPET_DEBUG=1` 才看得到），绝不抛异常、绝不输出。

**E19. 状态上报为什么 1 秒超时？**
A：它挂在热路径上，必须短。设计上限是 1 秒，超过就放弃（实测 daemon 不在时约 1.1 秒，含进程启动和连接开销）；审批路径可以等 130 秒，因为本来就在等人按键。

**E20. 代码结构/可维护性怎么样？**
A：电脑端分层清楚：`hook_client` 只管 Hook 协议，`Bridge` 管审批与记账，`SerialTransport` 管串口，传输层是鸭子类型的 4 方法契约。固件端是一个 `.ino`，约 984 行，带大量新手注释；可维护性一般，下一步会拆模块。测试是独立的 `_smoke_test*.py`，不依赖硬件。

### F 类 · 安全、可靠性与异常（22 题）

**F1. 贯穿项目的安全原则是什么？** ⭐
A：**拿不准就拒绝**。审批超时 → deny；daemon 连不上 → deny；解析失败 → deny；内部异常 → deny。任何异常都不得让 Hook 崩溃或放行。

**F2. 为什么超时要 deny，不是 allow？**
A：审批的本质是“人确认过”；没人确认就默认不执行。allow 会把“没看见”变成“批准了”，风险不可接受。

**F3. daemon 不在会怎样？** ⭐
A：审批事件会在连接失败/超时后返回 deny；状态事件静默失败；交互类工具（`AskUserQuestion`/`ExitPlanMode`）仍然 allow，因为设备表达不了多选项，终端原生交互必须继续。README 里专门写了“所有 Bash 命令都被拒绝？先看 daemon 开没开”。

**F4. 解析失败会怎样？**
A：电脑端：daemon 丢弃坏行，不影响进程；客户端解析失败 → deny。固件端：`vpJsonScan` 失败保留旧状态，不显示半截内容；超长行整条丢弃，后面的行不受影响。

**F5. 设备掉线会怎样？**
A：daemon 写失败 → `_invalidate()` 关端口 → `connection_loop()` 每 2 秒重连；设备端 5 秒收不到消息 → LOST，清 request_id，失联期间按键不回传。重连后设备先本地恢复，daemon 再补发当前状态。

**F6. 电脑睡眠/拔线/USB 接触不良？**
A：表现都是“设备收不到心跳 → LOST”。daemon 会重连；如果端口号变了，`discover_port()` 重新发现。审批进行中掉线，daemon 的 `_pending_approval` 还在，重连后重发审批卡（沿用原 id），但 120 秒超时仍然有效。

**F7. 按钮消息在串口上丢了会怎样？** 🔍
A：设备本地已经切到“已批准”，但 daemon 没收到按钮，会一直等到 120 秒超时返回 deny。这是**乐观反馈**的代价：屏幕说批准了，电脑说拒绝了。当前没有 ack/重发；改进方向是设备重发按钮直到收到 daemon 的确认，或 daemon 回一个 ack。

**F8. request_id 不匹配会怎样？**
A：daemon 丢弃按钮并记日志；不会误批准。设备端在收到新 state、按下按钮、进入 LOST 时都会清空 request_id，防止幽灵批准。

**F9. 多条审批同时来会怎样？** ⭐
A：daemon 用 `_approval_lock` 串行化，第二个请求排队等第一个走完；同一时间只有一个 `request_id`。这就是 F9 的“单槽”设计。缺点是第二条要等第一条最长 120 秒；多会话 FIFO 队列是下一步。

**F10. 多会话/多项目同时用呢？**
A：当前一个 daemon、一个单槽、一个屏幕，多个 Claude 会话的审批会串行；状态会互相覆盖（最后一条生效）。第一版没做多会话聚合；要做的话，需要给每个会话一个 id，屏幕上显示队列，daemon 维护 FIFO。

**F11. 设备复位会怎样？**
A：发 `hello`；daemon 收到后置 `_state_dirty` 并 `resend_current()`。如果复位时正在审批，`_pending_approval` 还在，会重发审批卡（原 request_id）；但设备端 `ridBuf` 已被复位清空，按钮要等新卡到达后才能用。

**F12. 电脑端崩溃/被 kill 呢？**
A：设备 5 秒后 LOST；重启 daemon 后会重新打开串口、补发当前画面。审批请求已经丢失，客户端会超时 deny。没有持久化队列，这是第一版的限制。

**F13. 串口被占用呢？**
A：打开失败，daemon 报“端口被占用”，每 2 秒重试；不会崩。烧录前必须先停 daemon，这也是 README 反复强调的。

**F14. 如果有人往串口里注入假消息呢？**
A：设备会把它当合法消息处理（协议没有认证）。威胁模型是“设备和电脑之间的线是可信的”；如果攻击者能碰你的 USB，他也能碰你的电脑。真要做安全，需要在协议里加签名/认证，当前没做。

**F15. 本地 Socket 有认证吗？** 🔍
A：没有，只绑 `127.0.0.1:8765`。本机任意进程都能连，能伪造审批请求。威胁模型假定本机可信；要加认证可以加一个 token，或改用带权限的命名管道/Unix socket。这是已知边界。

**F16. 审批内容会不会泄露敏感信息？**
A：daemon 默认日志只记事件、工具名、request_id，不把命令/文件摘要写进终端；但摘要会显示在设备屏幕上，屏幕是物理可见的。如果环境里有旁人，这是个隐私考虑。

**F17. 误触/静电/干扰？**
A：35 ms 稳定低电平 + 松开重武装，能过滤短毛刺；按钮两端可并联 100 nF 电容（设计文档 4.5）。曾经出现无人触碰却收到 deny，加去抖后 12 秒审批卡保持测试无误拒。

**F18. 看门狗会不会误判？**
A：心跳 1 秒、超时 5 秒，允许连续丢 4 个；而且任何合法消息都算保活。屏幕重绘几十毫秒不会影响。极端情况下 daemon 卡死超过 5 秒会判 LOST，这是预期行为——宁可显示失联，也不显示假状态。

**F19. 电源不稳/白屏？**
A：3.3V 50 mA 限制是头号嫌疑；改 5V（模块带 LDO）或换供电。设备没有电池，USB 供电质量也取决于电脑口；换一个 USB 口/带供电的 HUB 是排查手段。

**F20. 屏幕显示“已批准”但 daemon 拒绝，数据一致性怎么保证？**
A：屏幕是**乐观反馈**，最终决策以 daemon 为准；两者可能短暂不一致。当前没有 ack，长时间不一致只会在按钮消息丢失时出现。改进：设备重发按钮、daemon 回 ack、屏幕显示“待确认”。这是我知道的一个可靠性缺口。

**F21. 用户一直不按按钮呢？**
A：daemon 等 120 秒后 deny，客户端返回拒绝，Claude Code 不会执行。屏幕在设备端会一直停在审批卡，直到 daemon 发来下一条 state（审批结束后会发 working/idle）。

**F22. Claude Code 版本变了、Hook 格式变了呢？**
A：两个审批事件的输出格式是硬契约：`PreToolUse` 用 `permissionDecision`，`PermissionRequest` 用 `decision.behavior`。如果官方改格式，`hook_client.py` 的 `emit_decision()` 要同步改；测试里有两种格式的用例。Codex 的适配器也是单独一层，互不影响。

### G 类 · 测试与调试（18 题）

**G1. 有测试吗？** ⭐
A：有，104 例，全部不需要硬件：电脑端四套 49 例（hook_client 12、daemon 14、状态映射 14、串口传输 9），固件端离线 55 例（协议解析 + 字库取行）。

**G2. 104 例怎么分布？** ⭐

**G3. 一个业余项目为什么要写测试？** ⭐
A：这个项目出错的后果不是“显示错了”，而是“**该拒绝的没拒绝**”。这种东西靠手点几下根本测不出来；而且硬件不在手边时，测试是唯一能回归的手段。

**G4. 没有硬件怎么跑固件测试？**

**G5. 假串口怎么注入？**
A：`SerialTransport` 的构造函数接受 `serial_factory`，测试传一个假串口对象；`_smoke_test_serial.py` 用它模拟读、写、失败、重连。`--no-device` 模式用 `NullTransport`，按钮通过本地 Socket 注入。

**G6. 怎么测超时降级？**
A：daemon 测试里把 `approval_timeout` 设得很短，发审批请求后不按按钮，断言返回 deny；客户端测试里模拟 daemon 不响应/不存在，断言输出 deny。

**G7. 怎么测并发/单槽？**
A：daemon 测试里同时发两个审批请求，断言第二个排队、第一个的按钮不会串到第二个；还有“同一状态并发发送只下发一条”的用例。

**G8. 怎么测中文截断？**
A：构造超过 160 字节的中文摘要，断言截断后仍是合法 UTF-8、不出现半个汉字；固件端 `test_proto.cpp` 有 UTF-8 边界和 `\uXXXX` 的用例。

**G9. 怎么测字库？**
A：`gen_cn_font.py --verify` 用黄金字形（`中`、`A`）逐位比对；`test_proto.cpp` 测 `cnFontRow()` 的位序、索引 >255 不被截断、缺字返回 -1。

**G10. 怎么测按钮去抖？** 
A：真机上用 35 ms 滤波 + 12 秒审批卡保持测试，确认无误拒；离线没有按钮硬件，靠代码审查和真机实测。更好的做法是做一个硬件在环夹具，用继电器/舵机按按钮，当前没做。

**G11. 怎么测看门狗？**
A：串口探针 `--no-heartbeat`，等 5 秒看屏幕切 LOST；或者停掉 daemon。恢复时发心跳/状态，看是否回到最后有效状态。LED 行为也一起看。

**G12. 怎么测端到端？**
A：`_smoke_test_daemon.py` 里有端到端用例：起 daemon、模拟 hook_client 请求、注入按钮、断言决策。真机端到端是 Claude Code 跑一条命令，设备按批准/拒绝。

**G13. “屏幕空白”怎么定位？** ⭐
A：自底向上：① 跑 `tfttest_uno` 确认屏能亮；② 串口监视器看 `hello` 是否可读；③ 串口探针发 `/state working` 看画面；④ 发 `/approval` 看审批卡；⑤ 再查 daemon 和 Hook。不要一上来就怀疑上层逻辑。

**G14. “中文乱码/方框”怎么定位？**
A：方框 = 字不在字库里，加字重新生成；乱码 = 编码/截断问题，检查 UTF-8 边界、串口波特率、`F()`/PROGMEM。先区分“缺字”和“乱码”，处理方式完全不同。

**G15. 怎么测性能/延迟？**
A：状态刷新用高速摄像或逻辑分析仪看“daemon 发出 → 屏幕更新”；按钮响应用逻辑分析仪看“按钮按下 → TX 发出”。当前这些数字还没测，设计目标 ≤300 ms / ≤200 ms。

**G16. 怎么做 8 小时稳定性？**
A：写一个 soak 脚本循环发状态/心跳/审批，记录设备复位次数、丢行、daemon 日志；因为全部静态内存，理论上没有泄漏。当前还没跑 8 小时。

**G17. 测试有什么没覆盖？**
A：渲染效果（需要硬件/模拟器）、按钮物理抖动、电源异常、USB 拔插的时序、长时间稳定性、多会话并发、Codex 端到端。这些是下一步。

**G18. 如果给你硬件在环测试怎么做？**
A：用继电器/舵机按按钮，用 USB 转串口做回环，用摄像头 OCR 或电流传感器看屏幕/LED；CI 里跑 Python/C++ 测试，硬件测试单独跑。成本不高，但需要夹具和脚本。

### H 类 · 设计取舍与替代方案（20 题）

**H1. 为什么 UNO 不是 ESP32？** ⭐
A：ESP32 资源多、有无线，但屏幕在这块组合上点不亮；UNO 有已验证的显示例程，USB 口天然是数据链路。选型不是选最强，是选能做完的。

**H2. 为什么 Adafruit 不是 TFT_eSPI？**
A：v2.0 的 TFT_eSPI 只含 ESP32/ESP8266/RP2040/STM32 后端，没有 AVR 后端；U8g2 全量中文字体 202690 字节也装不进 32 KB。Adafruit + 自制子集字库是 UNO 能承受的组合。

**H3. 为什么自制字库不是 U8g2 全量？** ⭐
A：全量 202690 字节，是 32 KB Flash 的 6 倍多；只能裁。自制格式每字 20 字节，比 U8g2 平均 27.85 字节更小，因为设备端不需要解码器，直接存位图。

**H4. 为什么不用 ArduinoJson？**
A：Flash 多几 KB、动态池对 2 KB RAM 不可控；项目只需要取几个字段，自写 366 行（含注释）的解析器更省、更可控，还能离线测试。

**H5. 为什么不用 FreeRTOS？**
A：2 KB RAM 下任务栈开销大；并发需求简单（收串口、扫按钮、蜂鸣器），`millis()` 状态机足够。RTOS 会引入调度器和共享状态的复杂度，不划算。

**H6. 为什么不用动态内存？**
A：`malloc`/`new`/`String` 会碎片化 2 KB 堆，长期运行不可预测；全部静态缓冲，行为确定。代价是上限固定（一行 320 字节、字段 160 字节），但协议本来就限长。

**H7. 为什么单槽不是队列？** ⭐
A：第一版优先简单和正确：单槽 + 锁，逻辑清楚，测试好写；多会话 FIFO 队列是明确的下一步。单槽的缺点是第二条审批要等第一条 120 秒。

**H8. 为什么审批超时是 120 秒？**
A：人离开座位再回来，120 秒是个合理窗口；太短会频繁误拒，太长会把 AI 挂太久。客户端 130、Hook 150 是层层兜底，不让外部先杀。

**H9. 为什么 35 ms / 5 s / 1 s / 2 s？**
A：35 ms 去抖覆盖机械抖动且人感觉不到；5 s 看门狗允许丢 4 个 1 s 心跳；2 s 是 bootloader 启动时间；2 s 重连间隔避免刷屏。每个数都有“为什么不是更小/更大”的理由。

**H10. 为什么静态不是动画？** ⭐
A：动画版把 Flash 顶到 32098/32256，只剩 158 B，几乎不能加任何东西；而且用户觉得画面不够贴近 Clawd。改成静态后 Flash 30882（余 1374 B），画面更像官方吉祥物，也没有闪烁。代价是少了动效，但状态靠表情/道具区分足够。

**H11. 为什么是 Clawd？**
A：Clawd 是 Claude Code 的珊瑚橙像素螃蟹吉祥物，和项目主题强相关；米白底 + 经典橘是官方卡片风格，辨识度高。用表情和头顶道具区分七态，比文字更有趣。

**H12. 为什么有线不是无线？**
A：无线要配对、装驱动、管信号，而且 BLE 连接建立慢、独占；有线插上即用，USB 还同时供电。代价是必须插线，这是明确的取舍。

**H13. 为什么 TCP 不是 Unix socket/命名管道？**
A：跨平台（Windows/macOS/Linux）、标准库、调试方便；127.0.0.1 不经过网卡。Unix socket 在 Windows 上的 Python 3.9 兼容性不如 TCP。

**H14. 为什么 Python 不是 C++/Rust？**
A：开发速度、可读性、标准库；这个项目的数据量和频率都很低，Python 足够。启动开销对状态 Hook 有 1 秒预算，可以接受；如果真成瓶颈，可以把 daemon 换成编译语言，协议不变。

**H15. 为什么 128×160 不是更大屏？**
A：1.77" 模块便宜、常见、SPI 接线简单；128×160 竖屏能放标题 + Clawd + 4 行正文。更大屏要更多 Flash/RAM 和供电，UNO 扛不住。

**H16. 为什么 12px 不是 16px？**
A：12px 每行约 9 个汉字，4 行能放 36 个汉字；16px 字库体积约 1.8 倍，Flash 装不下，而且每行只能放 6–7 个字。12px 是清晰度和容量的平衡。

**H17. 为什么 request_id 8 位不是完整 UUID？**
A：8 个十六进制字符 = 32 位，单槽足够；完整 UUID 36 字符会占掉行长预算。它不是安全令牌，只是关联编号。

**H18. 如果加 WiFi/电池/外壳/多按钮，怎么做？**
A：WiFi：换 ESP32 或加 ESP-01，传输层换掉，协议不变；电池：加锂电 + 充电管理，注意功耗和 USB 数据；外壳：3D 打印，先量 UNO/屏幕/按钮位置；多按钮：扩展 `scanButtons()` 和 UI，但设备审批只有 approve/deny 语义，多按钮要重新设计。

**H19. 如果做产品化，缺什么？**
A：外壳、组装、成本核算、认证（如果有无线）、安装包/一键启动、日志与诊断、多会话、可靠性测试、用户文档。现在是原型，不是产品。

**H20. 这个项目最“工程”的决定是哪个？** 🔍
A：**审批期间不下发状态**。它不是功能，是一个真实 bug 的修复：屏幕上的审批卡会被后续状态顶掉，用户根本不知道有审批在等。修复需要理解 daemon 的记账、去重、单槽和重连，还要加回归测试——这是“工程”而不只是“写功能”。

### I 类 · AI 辅助与诚信（10 题）

### K 类 · 白板/现场题（14 题）

> 现场不一定会真让你写代码，但可能让你“讲思路”。先说出**输入/输出/边界**，再写伪代码。

**K1. 画一下架构图。** ⭐
A：三层：Claude Code/Codex → Hook 客户端（短命）→ 本地 Socket → daemon（常驻）→ USB 串口 → UNO 固件（屏幕/按钮）。画的时候标出两个方向：审批下行、按钮上行。

**K2. 写一个按钮去抖。** ⭐
A：思路：记录 `lowSince`；读到 HIGH 就清零并解锁；读到 LOW 且未锁存时开始计时；连续 LOW ≥35 ms 才返回 true 并锁存；松开后解锁。
```c
if (digitalRead(pin) == HIGH) { lowSince = 0; timing = false; latched = false; return false; }
if (latched) return false;
if (!timing) { lowSince = now; timing = true; return false; }
if (now - lowSince < 35) return false;
timing = false; latched = true; return true;
```

**K3. 写一个 UTF-8 安全截断。**
A：从上限位置往前退，直到当前字节不是续接字节（`(b & 0xC0) != 0x80`）；然后截断并补 `\0`。注意不要退到首字节之前。

**K4. 写一个行重组状态机。**
A：三个状态：正常累积、丢弃超长行、刚完成。收到 `\n`：正常则置 `ready`、复位长度；丢弃则复位 `dropping`、清长度。收到普通字节：正常且未满则写入；满了置 `dropping`。处理消息只摘 `ready`，不清长度（处理期间还会收新字节）。

**K5. 设计 request_id + 迟到按钮防护。**
A：daemon 生成 8 个十六进制字符的 id，发审批请求时存 `_pending_request_id`；只接受 `request_id` 匹配的按钮；超时/结束清槽；设备在收到新 state、按下按钮、LOST 时清本地 id。

**K6. 算最坏行长。**
A：骨架约 66 + request_id 8 + tool 24 + summary 160 = 258；上限 320，余 62。

**K7. 算 RAM/Flash 预算。**
A：RAM 1299：Serial 349 + 行缓冲 324 + msgBuf 161 + 其余 465；剩 749 给栈。Flash 30882：字库 9062 + 其余 21820；剩 1374。

**K8. 解释为什么没有 framebuffer。**
A：128×160×2 = 40960 B > 2048 B SRAM；直接画，整屏重绘切片。

**K9. 设计一个审批超时测试。**
A：daemon 设短超时（如 0.1 s），发审批请求，不注入按钮，断言返回 deny；再发第二次，注入第一次的迟到按钮，断言不影响第二次。

**K10. 设计多会话队列。**
A：每个会话一个 id；daemon 维护 FIFO（`asyncio.Queue`），一次只把队首发到设备；设备屏幕显示“第 1/3 条”；审批结果按 id 回给对应客户端；超时只影响队首。难点：状态显示与审批卡抢占屏幕、重连补发、公平性。

**K11. 加一个新状态。**
A：`enum` 加项、颜色、标题、Clawd 表情/道具、触发事件、恢复语义、文档、测试；检查 Flash。

**K12. 加一个新汉字。**
A：加进 `tools/cn_charset.txt`，跑 `gen_cn_font.py --verify` 和 `--out`，重新编译烧录；注意 Flash 只剩约 1.3 KB（按 23 字节/字算上限约 59 个，实际建议按 50 个左右规划）。

**K13. 如果把 320 改成 256 会怎样？**
A：最坏 258 字节的审批请求会被设备整条丢弃，屏幕空白，120 秒后超时拒绝，电脑端不知道。所以不能改小；要改小必须先缩短 summary/tool 或改协议。

**K14. 解释这段代码（现场指一段）。**
A：先说是哪一层（协议/状态/绘制/审批），再讲输入输出、关键边界、为什么这么写。不会的就说“这段是库/别人写的，我知道它解决的问题，但内部实现还要看”。

## 五、十条高频追问链

> 面试官不会只问一题，他会顺着你的回答往下挖。下面每条链都标了“下一层”，
> 练到能连着答三层，基本就稳了。

### 链 1：为什么两个程序？

1. 为什么分两个？→ 串口独占 + 打开复位 + Hook 短命。
2. 短命进程怎么跟常驻进程说话？→ 本地 TCP 127.0.0.1:8765，一行 JSON。
3. 为什么不用管道？→ 跨平台、标准库、调试方便。
4. daemon 不在呢？→ 审批 deny，状态静默，交互工具 allow。
5. 怎么保证不误批？→ request_id + 超时 deny + 设备本地清 id。

### 链 2：中文怎么显示？

1. 中文怎么显示？→ 12×13 子集字库，逐行位图。
2. 字库哪来的？→ U8g2 的 wqy12，裁 394 字。
3. 为什么不全量？→ 202690 B > 32 KB Flash。
4. 一个字多少字节？→ 20 位图 + 2 码点 + 1 步进 = 23。
5. 缺字怎么办？→ 空心方框，加字重新生成。
6. 怎么不切碎汉字？→ 按 UTF-8 字符边界退。

### 链 3：320 字节怎么来的？

1. 为什么是 320？→ 最坏 258，留余量。
2. 258 怎么算？→ 骨架 66 + id 8 + tool 24 + summary 160。
3. 为什么 summary 160？→ 约 53 汉字，屏幕只显示约 36，超出 `..`。
4. 工具名太长呢？→ tool 限 24，截断不顶爆整行。
5. 改成 256 会怎样？→ 整条静默丢弃，屏幕空白，超时拒绝。

### 链 4：3 ms 怎么来的？

1. 为什么 3 ms？→ 115200 约 11.5 B/ms，3 ms 约 35 B。
2. 缓冲多大？→ 默认 64（5.5 ms），提升 256（22 ms）。
3. 怎么保证？→ 整屏切片 8 行、每字/每行 `pumpSerial()`。
4. 蜂鸣器呢？→ 非阻塞状态机，不能用 delay。
5. 如果某次绘制超了？→ 可能丢字节，协议行不完整，整条被丢弃；所以要切片。

### 链 5：按钮去抖？

1. 怎么去抖？→ LOW 稳定 35 ms + 松开重武装。
2. 为什么 35 ms？→ 机械抖动通常十几 ms，35 ms 人感觉不到。
3. 长按呢？→ 锁存到松开，只算一次。
4. 两个同时按？→ 批准优先（代码顺序），可以改成拒绝优先。
5. 误触 deny 怎么回事？→ 空闲 D2/D3 为 HIGH，但曾收到 deny；加去抖后 12 秒无误拒。

### 链 6：request_id？

1. 干什么？→ 按钮和审批一一对应。
2. 不加会怎样？→ 迟到按钮误批准下一次。
3. 8 位够吗？→ 32 位，单槽，碰撞概率 1/2^32，不是安全令牌。
4. 重连呢？→ 重发审批卡，沿用原 id。
5. 设备什么时候清 id？→ 收到新 state、按下按钮、LOST。

### 链 7：看门狗/LOST？

1. 怎么判断失联？→ 5 秒没任何合法消息。
2. 为什么任何消息都算？→ 只要电脑还在说话，链路就通。
3. 恢复策略？→ 回最后有效状态；审批/交互卡转 IDLE 并清正文。
4. 失联时按按钮？→ 不回传，id 已清。
5. 重连补发？→ `resend_current()`：审批中重发卡，否则重发最后 state。

### 链 8：审批卡被顶掉？

1. 现象？→ 多条审批挤在一起时，有的审批不显示。
2. 原因？→ 批准后 `PostToolUse` 上报 working，把下一条审批卡刷掉。
3. 修复？→ 审批期间只记账不下发；`_state_dirty` 保持。
4. 怎么防回归？→ daemon 测试用例 14。
5. 还有类似问题吗？→ 去重、重连补发、审批后状态都要考虑 `_state_dirty`。

### 链 9：AI 参与？

1. 是不是 AI 写的？→ 用了 AI，但需求和决策是我的。
2. 你会写代码吗？→ 会基础，能读懂、能改、能调试。
3. 哪个 bug AI 没解决？→ 白屏、审批卡被顶掉、无人触碰 deny。
4. 你怎么验证？→ 编译、测试、真机行为。
5. 你能对结果负责吗？→ 每个设计决定能解释，不会的承认。

### 链 10：如果加功能？

1. 多会话队列？→ `asyncio.Queue` + 会话 id + 屏幕队列显示。
2. 无线？→ 换传输层（HC-05/ESP32），协议不变。
3. 外壳？→ 3D 打印，先量尺寸。
4. 电池？→ 锂电 + 充电管理，注意功耗。
5. OTA？→ UNO 没有 OTA，要换板/加 bootloader；当前不做。

## 六、代码导览：被点开一段怎么办

> 策略：**先讲这段解决什么问题，再讲关键边界，最后讲踩过的坑。**
> 不要从第一行开始逐行念。

### 6.1 首选三段（练到不看注释也能讲）

#### ① `pc/hook_client.py` 的 `emit_decision()`

- **解决什么问题**：Claude Code 的两个审批事件格式不同，`PreToolUse` 用
  `permissionDecision`，`PermissionRequest` 用 `decision.behavior`；不能串。
- **关键边界**：stdout 只允许这一行 JSON；日志全走 stderr；写字节用
  `sys.stdout.buffer`，避免 Windows GBK 编码崩溃。
- **可以补一句**：状态事件 stdout 必须零字节，否则会污染 Hook 通道。

#### ② `firmware/VibePet_UNO/VibePet_UNO.ino` 的 `buttonPressedStable()`

- **解决什么问题**：机械按钮会抖，短毛刺会导致误批准/误拒绝；长按会连续触发。
- **关键边界**：LOW 连续稳定 35 ms；按下后锁存，松开才重新武装；每个按钮独立状态。
- **踩过的坑**：无人触碰却收到 deny，诊断空闲引脚为 HIGH；加去抖后 12 秒审批卡无误拒。

#### ③ `firmware/VibePet_UNO/vibepet_proto.h` 的 `vpLineFeed()`

- **解决什么问题**：串口一次读到的字节不保证是一条完整消息；可能半条、可能两条半。
- **关键边界**：按字节攒、遇 `\n` 才置 `ready`；超长行 `dropping` 到行尾；处理消息只摘
  `ready`，**不清长度**（处理期间还会收下一条的开头）。
- **踩过的坑**：清空长度会把下一条消息截断，表现为“屏幕什么都没有”。

### 6.2 备选四段

#### ④ `pc/bridge_daemon.py` 的 `_on_device_line()`

- 校验 `hello`、`button`、`action`、`request_id`；只接受当前等待中的 id。
- 讲“迟到按钮”场景：审批超时后按下去，不能批准下一次。

#### ⑤ `pc/bridge_daemon.py` 的 `send_state()`

- 去重键 `(status, msg)`；`_state_dirty` 记账；审批期间只记账不下发。
- 讲“审批卡被顶掉”的真实 bug 和用例 14。

#### ⑥ `firmware/VibePet_UNO/VibePet_UNO.ino` 的 `beepService()`

- `beepStart()` 只设节奏，`beepService()` 每轮推进；从不用 `delay()`。
- 讲 120 ms 阻塞会积压约 1380 字节，256 缓冲也溢出。

#### ⑦ `firmware/VibePet_UNO/cn_font.h` 的 `cnFontRow()`

- 13 行 × 12 位连续打包；`bit0 = 最左`；索引 16 位。
- 讲两个踩过的坑：镜像列、`uint8_t` 截断索引。

### 6.3 如果被点到你讲不了的

别硬撑：

> “这块是我照着文档/库实现的，具体原理我还得再学。不过我知道它解决什么问题——
> 比如这里是为了不丢串口字节/不切碎汉字/防止迟到按钮。”

然后可以把话题拉回你懂的边界：**输入输出、为什么需要、失败了会怎样**。

### 7.3 故障树

| 现象 | 先查什么 | 怎么说 |
|---|---|---|
| 屏幕不亮 | USB 线是不是数据线；VCC/GND/LEDA；3.3V 50 mA | “先排除供电和接线，再怀疑代码” |
| 屏幕背光亮、无画面 | 供电不足；初始化序列 | “3.3V 改 5V（模块带 LDO）；换 INITR_*” |
| 屏幕显示 LOST | daemon 没开/线松/板子复位 | “先启动 daemon；打开串口会让板子复位，等 2 秒” |
| Claude Code 所有 Bash 被拒 | daemon 没启动 | “这是 fail-closed 设计，不是 bug” |
| 按按钮没反应 | 按钮接错（同侧两脚）、没接 GND、串口被占 | “微动开关要跨对角接；先停串口监视器” |
| 蜂鸣器只“咔哒” | 有源蜂鸣器 | “固件按无源驱动；有源把 BUZZER_ACTIVE 改 1” |
| 中文显示方框 | 字不在字库 | “加进 cn_charset.txt 重新生成” |
| 中文乱码 | 波特率/编码/截断 | “先看 115200 是否可读，再查 UTF-8 边界” |
| 端口被占用 | Arduino IDE 串口监视器/另一个 daemon | “烧录前先停 daemon” |
| 演示时 Claude Code 没触发审批 | Hook 配置/权限 | “用 `--no-device` 或直接跑 hook_client 命令行” |

> **真实彩蛋**：写这份文档时，我自己的 Hook 就把一条 `grep` 拦了——daemon 没启动，
> `PreToolUse` 直接返回 deny。这正好证明了 fail-closed 的行为：不是 bug，是设计。
> 如果面试时遇到“怎么证明它真的会拦”，这就是一个现成的例子。

## 附录 A：术语表

| 术语 | 解释 |
|---|---|
| Hook | 宿主程序在特定事件发生时调用的外部命令 |
| `PreToolUse` | Claude Code 在工具执行前触发；本项目用它拦 Bash |
| `PermissionRequest` | Claude Code 需要权限决定时触发；覆盖非 Bash 工具 |
| `hookSpecificOutput` | Claude Code Hook 返回决策的 JSON 外壳 |
| `permissionDecision` | `PreToolUse` 的决策字段：allow/deny/ask/defer |
| `decision.behavior` | `PermissionRequest` 的决策字段：allow/deny |
| JSON Lines | 一条消息一行 JSON，按换行切分 |
| request_id | 审批请求的关联编号，按钮回传必须匹配 |
| 单槽 | 同一时间只处理一个审批请求 |
| fail-closed | 拿不准就拒绝 |
| fail-open | 拿不准就放行（本项目审批路径不用） |
| 看门狗 | 超时未收到消息就切换失联状态的机制 |
| 去抖 | 过滤按钮机械抖动 |
| 非阻塞 | 不占用主循环等待，用状态机推进 |
| PROGMEM | AVR 的 Flash 常量存储属性 |
| RGB565 | 16 位颜色：5 红 + 6 绿 + 5 蓝 |
| framebuffer | 整屏像素缓存 |
| UTF-8 | 变长编码；汉字通常 3 字节 |
| asyncio | Python 异步 I/O 框架 |
| `call_soon_threadsafe` | 从其他线程安全地把回调投递到事件循环 |
| 半关闭 | TCP `SHUT_WR`：只关发送方向，保留接收 |
| boot grace | 打开串口后等 bootloader 走完的 2 秒 |
| 乐观反馈 | 设备先本地切画面，不等电脑确认 |
| 硬件在环 | 用真实硬件参与自动化测试 |
